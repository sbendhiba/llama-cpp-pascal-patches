# v0.6.0 on 2x P100 — speed baseline for Q4_1 and UD-Q4_K_M, and the MTP head

Measured 2026-10-13 on `x99dual`, 46-patch tree. Stock arm `~/llama.cpp-v0.6.0`, patched arm
`~/llama.cpp-v0.6.0-p100`, both build line `d81235049 (11429)` = llama.cpp `v0.6.0`. Two new
quantizations of the same 27B the rest of this directory measures, added because the two files already
in use (Q4_0 and the 35B MoE's UD-Q4_K_M) do not cover the quant types the remaining patch candidates
target.

Speed only — no perplexity, no `-npl`, deliberately. `-fa on -t 28 -ub 2048 -p 512,2048 -n 128`,
5 rounds per arm, arms interleaved with the order reversed on even rounds, cards cooled to 45 C between
configs. Raw rows: `v0.6.0-p100x2-base-{q41,q4km}-{tensor,layer}.csv`.

## What these rows say

**The `pp512` gain is patch 51, on both splits.** Under `-sm layer` no AllReduce runs at all, yet
pp512 still moved +41.4% and +40.3% — that is the cuBLAS algorithm choice, and it is larger than the
same-column numbers in the README's shipped table for Q4_0 (which were taken before patch 51 existed,
hence flat). Consequence: the README's prefill columns are now stale at short prompts on every
quantization, and the honest fix is a full re-take of the headline table, not another footnote.

**`pp2048` at +8% is the AllReduce and the scheduler patches, not the algorithm** — 2048 rows is where
ALGO6 stops being the faster kernel, which is what patch 51's own A/B measured (−0.8% at pp2048).

**Decode ranks by quantization the way the GEMV cost table predicts.** Patched tensor-split decode:
Q4_1 **34.58**, Q4_0 33.63, UD-Q4_K_M **28.79** t/s. Q4_K is 17% slower than Q4_1 on the same model
and the same path, and the source fork's `test-backend-ops` GEMV numbers put Q4_1 at 110.7 µs against
Q4_K at 152.0 µs on a 4096×14336 shape on this exact card — an independent measurement agreeing that
Q4_K's dequant is the expensive one on GP100. That is also the strongest argument for taking their
per-quant-type matvec rebuild next: the type where our decode is slowest is the type their work
targets and ours (patch 12, Q4_1 only) does not.

**Stock Q4_1 is faster to decode than stock Q4_0** (24.70 against 23.27 t/s) while its prefill is
slightly slower (225.13 against 229.83 at pp512) — a small thing, but it means the usual "Q4_1 costs
speed for quality" intuition is not true on this card.

## MTP smoke — the head is live, and the shape of the problem is already visible

Not a baseline, one run each, `llama-cli -st` on Q4_1 `-sm tensor -c 4096 --temp 0 -s 123 -n 192`,
greedy, ~400-token context:

| arm | generation t/s |
|---|---:|
| no speculative decoding | 34.2 |
| `--spec-type draft-mtp --spec-draft-n-max 2` | **44.9** (+31%) |
| `--spec-type draft-mtp --spec-draft-n-max 4` | 37.3 (+9%) |

The built-in nextn head drafts correctly and is worth +31% at n-max 2 — but n-max 4 is *worse*, which
is exactly the wall the source fork describes: a wider verify is not free (their measured verify cost
is 46/53/58/64 ms for 2/3/4/5 tokens), the graph is rebuilt whenever the verify width changes, and so
their answer was a fixed-width padded verify plus a draft length that shortens with context depth.
Full acceptance/depth behaviour is the user's own real-test-case validation, deliberately not done
here.

Flag note for anyone repeating it: `--spec-type` is registered only for `llama-cli`, `llama-server`,
`llama-speculative` and the lookup tool — `llama-bench` and `llama-completion` reject it, and
`llama-cli` has no `-no-cnv` in this version, use `-st` / `--single-turn`.
