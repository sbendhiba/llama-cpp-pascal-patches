# v0.6.0 on 2x P100 — what the tensor-parallel exchange actually costs

2026-10-13, `x99dual`, one binary (the 46-patch arm `~/llama.cpp-v0.6.0-p100`, build line
`d81235049 (11429)`), arms differing only by an environment variable in a wrapper bin dir.
Qwen3.8-27B Q4_0, `-sm tensor -fa on -t 28 -ub 2048 -p 2048 -n 128`.

This is the cost structure behind the next candidate from
[Kmic-68/llama.cpp](https://github.com/Kmic-68/llama.cpp), commit `1f92a1b48` — *overlap the prefill
tensor-parallel exchange with the matmul, in token chunks* (+4.5% pp2048, bit-identical on their
board). Two questions had to be answered before writing any code: how much of our prefill is the
exchange, and is the primitive that overlap needs even available here.

## 1. Wire bytes and exchange mechanism (`…-xchg-cost.csv`, 5 rounds)

| arm | switch | pp2048 | tg128 | delta pp2048 |
|---|---|---:|---:|---:|
| `wire-bf16` | shipped default | **400.61 ± 2.94** | 33.56 | — |
| `wire-f32` | `GGML_CUDA_AR_BF16_THRESHOLD=0` (f32 on the wire, 2x bytes) | 366.72 ± 2.00 | 33.43 | **-8.46%** |
| `copyeng-off` | `GGML_CUDA_AR_COPY_THRESHOLD=0` (SM chunked kernel instead of the copy engines) | 396.75 ± 1.41 | 33.55 | -0.96% |

Doubling the bytes on the wire costs 8.46% of the pass, so the transfer itself is roughly **9% of
pp2048** and that is the ceiling for anything that hides it. Which mechanism moves those bytes is
almost irrelevant: the copy-engine path is worth 1% over the SM kernel path. Both numbers are decode
-insensitive (-0.02%, -0.36% at tg128), as expected — decode exchanges are under the 1 MB threshold
and take the chunked kernel path anyway.

Peer access is not the missing thing on this board either: `nvidia-smi topo -m` reports **PHB**
between the two cards, same NUMA node, and `nvidia-smi topo -p2p r` / `-p2p w` are both `OK`. So the
fork's line "internal AllReduce on Pascal is 17% slower, it assumes NVLink" is a statement about
*serialization*, not about P2P — which is consistent with their own +44.5%-equivalent coming from
overlapping rather than from a different transport.

## 2. The knob in patch 49 that is still off (`…-xchg-knob.csv`, 4 rounds)

| arm | switch | pp2048 | tg128 | delta pp2048 |
|---|---|---:|---:|---:|
| `default` | shipped | 399.53 ± 2.41 | 33.54 | — |
| `h2d-on` | `GGML_CUDA_AR_H2D_STREAM=1` | **413.38 ± 1.64** | 33.54 | **+3.47%** |
| `chunk-8m` | `GGML_CUDA_AR_COPY_CHUNK_BYTES=8388608` | 399.53 ± 1.15 | 33.54 | +0.00% |
| `chunk-1m` | `GGML_CUDA_AR_COPY_CHUNK_BYTES=1048576` | 398.49 ± 0.86 | 33.52 | -0.26% |

The second copy engine (stage 2's H2D on its own stream) is worth **+3.47% of prefill and nothing at
decode** — the first time it has been measured on its own rather than bundled with the Pascal gate.
The chunk-size heuristic (`nbytes/4` clamped to 512 KB..2 MB) is already at its optimum: 4x bigger
chunks change nothing, 2x smaller costs 0.26%. No tuning win there.

Absolute levels are ~5% below the `…-g50` session for the same binary and config (cards at 45-60 C
here against 38-56 C there); per the repo rule these rows are only read as within-session deltas.

## 3. The blocker: an external stream cannot wait on an in-graph event

The overlap needs the producing matmul chopped into token chunks *with an event per chunk*, and the
AllReduce — which is host-enqueued by the meta backend **between** subgraphs
(`ggml/src/ggml-backend-meta.cpp:2450-2466`) — waiting on chunk *c*'s event while chunk *c+1* still
computes. Since patch 50 is on by default, that producer is inside a captured graph.
`benchmarks/tools/graph-event-wait.cu` tests exactly that on this card (CUDA 12.4, sm_60), graph =
`[writer] -> [record ev] -> [spin ~300 ms]`, then `cudaGraphLaunch` on s1 and
`cudaStreamWaitEvent(s2, ev)` plus a reader on s2:

| attempt | result |
|---|---|
| `cudaEventRecord(ev, s1)` during capture (Relaxed — the mode llama.cpp uses) | the capture leaves **no event node** (3 ops, 2 nodes) and the external wait returns `invalid argument` |
| `cudaGraphAddEventRecordNode` after the spin (graph end) | the wait is accepted, the dependent launch then fails `invalid argument` |
| `cudaGraphAddEventRecordNode` after the writer (mid-graph) | every call "succeeds" and the reader observes `flag == 0` — **the wait did not track the in-graph record at all** |

The third row is the one that matters: it fails silently, which is the same class as the two cross-stream
races the fork found sitting behind a green `test-backend-ops`. On this stack, a graph is a closed
object to the host: nothing enqueued outside it can synchronise on anything inside it.

## 4. What that prices

Porting `1f92a1b48` to our tree means the producer must be **ungraphed**. Concretely: chunk the
single-matrix branch of `ggml_cuda_mul_mat_cublas_impl` (`ggml-cuda.cu:1587`) along `ne11` together
with its fp16→fp32 output convert (`:1665`), record an event per chunk, mark the subgraph's last node
the way their `xchg_want` does, and replace the whole-matmul `wait_for_compute` in
`ggml_cuda_ar_allreduce_copy_impl` (`allreduce.cu:733`) with a per-chunk wait — plus disable graph
capture for those prefill subgraphs. That last part is nearly free: patch 50's own prefill effect is
-0.07% (27B dense tensor), -0.15% (MoE tensor) and -0.03% (MoE layer), because graphs earn their
living at decode, where this overlap does not apply. Ceiling ~9%, their realized number +4.5%, so a
plausible net here is +3-4%.
Estimate: 250-350 lines across the two files that carry the most risk in the set, in the one patch
that still has no output-identity check.

Against that, `GGML_CUDA_AR_H2D_STREAM` **default-on is a one-line change in the same patch**, worth
+3.47% prefill and free at decode, on a code path that is already shipped, already reviewed and
already covered by `benchmarks/ppl.sh`.

**Status: the overlap is not ported.** The ceiling and the blocker are recorded above so the next
person does not start from the fork's +4.5%. The H2D-stream flip is measured and not yet adopted —
the right gate for it is `test-backend-ops` on the patched tree (never run, owed since patch 50) plus
the paired-perplexity arms, because the change is a synchronisation change, not a math change.
