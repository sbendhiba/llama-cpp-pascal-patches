# v0.6.0 on 2x P100 — MTP verify width, and why the fork's MTP patches were not ported

Measured 2026-10-13 on `x99dual`, 46-patch tree, `Qwen3.8-27B-Q4_1` (16.3 GiB), `-sm tensor -ngl 99
-fa on -t 28 -c 4096 --temp 0 -s 123 -n 192 -st`, three repeats per arm, widths interleaved. The
prompt is one fixed ~24-token question, so this is a shape study, not a quality study — the real-world
validation is deliberately left to a production test case.

## MTP is worth a lot, and the default width throws away a third of it

| `--spec-draft-n-max` | generation t/s | vs no speculation |
|---:|---:|---:|
| 0 (none) | 34.17 | — |
| 1 | 45.57 | +33.4% |
| **2** | **48.13** | **+40.9%** |
| 3 (the build's default) | 41.97 | +22.8% |
| 4 | 40.23 | +17.7% |
| 5 | 35.67 | +4.4% |

Repeat-to-repeat spread never exceeded 0.3 t/s. The peak is at two drafts, and it is sharp: at
`n_max 3`, which is what `llama-cli` picks when asked for MTP and nothing else, this build runs 13%
slower than it has to, and at 5 the benefit is nearly gone.

That is a setting, not a patch — on this hardware, with this model, `--spec-draft-n-max 2` is the
correct flag and there is nothing in the patch set to change to get it.

## Why the width decays, and what that says about the port

`--spec-draft-p-min` defaults to **0.00** in this build, so in the table above the draft always ran to
`n_max`: every verify had the same shape and the graph was never rebuilt. Adding a probability stop on
top of that:

| width | `p_min` 0 | `p_min` 0.2 | `p_min` 0.5 |
|---:|---:|---:|---:|
| 2 | 47.97 | 47.87 | 34.57 |
| 3 | 41.73 | 41.73 | 29.53 |
| 5 | 35.47 | **33.93** | 24.40 |

At 2 and 3 the stop essentially never fires, so it costs nothing. At 5 it fires and **loses 4.3%**. A
shorter draft gives up accepted tokens faster than it saves verify work at this depth. The source
fork says the same thing and locates its own exception precisely: their measured verify cost was
46/53/58/64 ms for 2/3/4/5 tokens, so "a rule that stops drafting once the product of the draft
probabilities falls under a threshold **only pays where a verify token is expensive**" — at 2k
context it does not, and their +16% is a 260k number.

## What this decides

The candidate list asked whether to port the fork's speculative-decoding work. Auditing our tree
answered it: `common/speculative.cpp` already has sampled drafts (per-sequence draft samplers with
their own temperature and top-k), the lossless rejection rule ("rejection weighs q against p, so both
have to sample alike"), `p_min`/`n_min`/`n_max` draft stopping, MTP block-size clamping, and the K/V
catch-up path. The single thing missing is the fixed-width padded verify and the
`llama_set_n_active_tokens` API behind it — and that mechanism exists to make *variable* draft widths
cheap. Our widths are already fixed, because the default threshold never fires; on this box at this
depth, porting it would buy nothing and, without their q6_K matvec and q4p attention computing only
the real tokens, padding could only make the verify wider, never narrower.

So: **not ported.** What is still worth taking from their speculative work is whatever makes a wide
verify cheaper rather than rarer — their exact-fit attention tile (`8599fe022`, 1.24× on a 5-token
verify, where the padding is 37% of the work) is the one that attacks the cost directly, and it is
CUDA-side. Whether it transfers depends on our model's GQA fold matching their head-256/GQA-6
geometry, which is the first thing to check.
