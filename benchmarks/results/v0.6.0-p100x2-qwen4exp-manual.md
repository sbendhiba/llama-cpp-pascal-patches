# v0.6.0 / b11539 on 2x P100 — Qwen3.8-Flash-Next IQ1_M, by hand

Transcribed from three manual `llama-bench` runs supplied on 2026-10-11, **not** from
[`../run.sh`](../run.sh): the arms were not interleaved and no temperature or environment was
recorded. It is the first row this set has on a model that does not fit in the cards, and the first
with a prompt-processing *loss* big enough to need explaining, which is why it is filed separately
rather than folded into the scripted table.

Machine `x99dual`: 2x Tesla P100-PCIE-16GB (32,538 MiB), `-t 28`, 5 reps per cell, `--progress`.

Model: `ISTA-DASLab/Qwen3.8-Flash-Next-GSQ-RCO-Coder-GGUF`, `IQ1_M`, shard
`...-00001-of-00002.gguf`. llama-bench's own row for it reads **`qwen4exp A3B IQ1_M - 1.75 bpw`,
54.39 GiB, 116.51 B params** — that triple is internally inconsistent (1.75 bpw over 116.51 B is
~25 GB, not 54.39 GiB), and with 54.39 GiB reported against 32.5 GiB of VRAM most of the weights
cannot be resident on the cards. Take these rows as a partly-offloaded run on a qwen4exp MoE and
**not** comparable to the fully-offloaded 27B/35B rows in
[`v0.6.0-p100x2-summary.md`](v0.6.0-p100x2-summary.md).

`-fa on -ub 2048 -n 128 -lm mmap`, prompt `-p 512`. A 512-token prompt is a single ubatch at
`-ub 2048`, so pp512 and the pp2048 columns elsewhere in this repo are different code paths at
different batch shapes: this is its own measurement, not a proxy for a pp2048 number.

## What this does and does not say

**It is the largest prompt-processing loss the set has produced.** Every scripted row so far is within
a point of flat on pp (27B tensor −0.5%, 35B tensor −0.7%, 27B layer +1.8%, 35B layer +4.2%). −5.1%
and −6.1% here are an order of magnitude beyond that, on the one model family in the repo with
architecture-specific patches of its own (42 `qwen4exp-hc-exact`, 46 `qwen4exp-moe-expert-cache`,
47 `sched-split-inputs-cap`). Nothing here identifies the cause: the whole set was measured, not its
members, and no kill-switch A/B has been run. That is the open follow-up.

**The AllReduce patch cannot be the cause of these particular rows** — with `GGML_CUDA_AR_PASCAL`,
`GGML_CUDA_AR_H2D_STREAM` and `GGML_CUDA_AR_NGPU` unset, `ggml_cuda_ar_pipeline_init` refuses
`cc < GGML_CUDA_CC_VOLTA` and returns `nullptr` on a P100 exactly as stock does, so the patched arm
takes the same meta-backend fallback as the stock arm and none of the rewritten kernels execute.
Caveat: nobody recorded whether those variables were exported for these runs. If `GGML_CUDA_AR_PASCAL`
was set, the two `-sm tensor` rows *do* include the internal AllReduce and would be measuring a
different reduction than stock's fallback — the `-sm layer` rows would not, because a layer split
never issues the cross-device reduce.

**The b11539 arm is not a control.** There is no stock `b11539` number, so the third row of each pair
mixes the llama.cpp version with the 39-vs-44 patch rebase and with the absence of patch 49. All it
shows is that the `b11539` set runs ~0.7-1.5% *slower* than the `v0.6.0` set on this model, on both
splits and both tests — which is the opposite of what `b11539`'s unmoved decode rows claim for the
newer tree, and is another reason that branch has never been taken as a release.

**Split choice, third confirmation of the existing rule.** Patched-`layer` gains more over
stock-`layer` (+20.3%) than patched-`tensor` gains over stock-`tensor` (+13.1%), yet `tensor` is
faster outright in both arms and on both tests — 346.72 against 243.43 and 28.18 against 25.96. Same
conclusion as the 27B: never recommend `-sm` from a delta.

## What is missing before this becomes a number to quote

- interleaved arms with the order reversed, from [`../run.sh`](../run.sh), at a recorded temperature;
- the `env` column, i.e. whether the AllReduce variables were set;
- at least one cell at `-p 2048`, so this model sits on the same prompt-shape axis as the others;
- a `-npl` or perplexity check, which no row in this repo has;
- the kill-switch A/B that finds the pp loss.
