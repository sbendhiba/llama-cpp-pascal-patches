# v0.6.0 on 2x P100 — CUDA graphs on sm_60: rejected once, then adopted on a second look

Started from [llama.cpp#27721](https://github.com/ggml-org/llama.cpp/pull/27721) (open, unmerged as of
2026-10-12): one line that moves the architecture gate in `ggml_cuda_graph_set_enabled` from
`GGML_CUDA_CC_VOLTA` to `GGML_CUDA_CC_DP4A` (610). That unlocks sm_61 and **leaves sm_60 — GP100,
this box — gated off**, which the author states himself; he has no sm_60 to test. So the PR as
written does nothing for a P100, and the question became whether the same line one arch further
down (`GGML_CUDA_CC_PASCAL`, 600) helps here.

It does, but not for every configuration, and the first pass got the decision wrong in the
conservative direction. Both passes are in this file because the reversal is the interesting part.

## First pass — 2026-10-12 morning, `-p 512`, 3 rounds, **not adopted**

One build. `graphs_on` is the build directory; `graphs_off` is a directory holding a wrapper named
`llama-bench` that exports `GGML_CUDA_DISABLE_GRAPHS=1` and execs the same real binary — upstream's
`is_enabled()` is `!(disable_due_to_gpu_arch || disable_cuda_graphs_due_to_env)`, so with the arch
gate flipped that env var is a clean switch inside one compilation. Consequence for the csv: the
`env` column reads `none` on every row, because the switch lives in the arm, not the runner.
Interleaved, order reversed on even rounds, cards cooled to 45 C between configs.

| config | pp512 | tg128 |
|---|---:|---:|
| 27B dense `-sm layer` | +0.21% | −0.76% |
| 27B dense `-sm tensor` | +0.05% | −1.00% |
| 35B-A3B MoE `-sm layer` | **−1.14%** | **−2.95%** |
| 35B-A3B MoE `-sm tensor` | −0.60% | **+12.21%** (78.56 ± 0.04 vs 70.01 ± 1.11) |

Rejected on the reasoning that a single arch constant cannot encode "only when the MoE is on a
tensor split", and that `ggml_cuda_graph_set_enabled` cannot see which split mode created its
context. Raw rows: `v0.6.0-p100x2-graphs-{27b,35b}-{layer,tensor}.csv`.

## Second pass — the one that won, at the shape the README reports

`-p 4096 -n 128 -ub 2048`, 5 rounds, same two arms, same single build. This was prompted by the
observation that #27721's author reports his gain **shrinking** as context grows — graphs remove a
fixed per-token cost, so a deep KV should dilute it — which meant +12.2% measured at ~640 tokens of
KV was not a number to ship on.

| config | pp4096 on vs off | tg128 on vs off |
|---|---:|---:|
| 35B-A3B MoE `-sm tensor` | 1169.54 vs 1171.33 (−0.15%) | **78.33 ± 0.06 vs 69.65 ± 1.56 (+12.46%)** |
| 35B-A3B MoE `-sm layer` | 952.64 vs 952.96 (−0.03%) | **68.23 ± 0.04 vs 70.67 ± 0.07 (−3.45%)** |
| 27B dense `-sm tensor` | 410.01 vs 410.31 (−0.07%) | 33.50 ± 0.10 vs 33.81 ± 0.03 (−0.92%) |

Three things fell out. The gain does **not** shrink with context on this card: +12.21% at pp512,
+12.46% at pp4096. The prefill loss from the first pass does not reproduce: MoE layer pp512 was
−1.14%, pp4096 is −0.03%, so that was the prompt shape and not the patch. And the winning arm is
the stable one — 78.33/78.31/78.36/78.35/78.33 while graphs-off swings 1.56 wide.

## Output is unchanged

Same corpus (`wikitext-2-raw`, 8 chunks of `-c 2048`, `-ub 512`), same binary, both switch
positions, and again on the shipped defaults with no environment set at all:

| arm | PPL |
|---|---:|
| 27B `-sm layer`, graphs on | 5.2538 ± 0.13730 |
| 27B `-sm layer`, graphs off | 5.2538 ± 0.13730 |
| 35B `-sm tensor`, graphs on | 4.8859 ± 0.12403 |
| 35B `-sm tensor`, graphs off | 4.8859 ± 0.12403 |
| 35B `-sm tensor`, shipped defaults (49 + 50 both on, no env) | 4.8859 ± 0.12403 |

Identical to four decimals, which is what a replay should do — a graph does not reassociate
anything. The 27B figure also reproduces the `-sm layer` control from
[`v0.6.0-p100x2-tensor-27b-perplexity.md`](v0.6.0-p100x2-tensor-27b-perplexity.md) exactly, across a
box reboot.

## Adopted as patch 50, on by default

The reversal is because of two things the first pass under-weighted. The opt-out already exists
upstream and takes effect per run — `GGML_CUDA_DISABLE_GRAPHS=1`, no rebuild — which makes a
default-on arch flip a materially different decision from 49's gate, where the only escape was a
recompile in the other direction. And the one configuration that pays, MoE under `-sm layer`, is
already the wrong split for that model in this build: 1169.88 / 78.38 on tensor against
952.76 / 68.25 on layer, so the loss lands on a path the README does not recommend.

What the shipped defaults then measure against stock, 5 interleaved rounds, both arms
`d81235049`, nothing in the environment:

| config | pp | tg128 |
|---|---:|---:|
| 27B dense `-sm tensor` | pp512 229.83 → 242.88 (**+5.7%**) / pp2048 382.53 → 419.46 (**+9.7%**) | 23.27 → **33.63 (+44.5%)** |
| 35B-A3B MoE `-sm tensor` | pp4096 1091.65 → **1169.88 (+7.2%)** | 57.88 ± 3.11 → **78.38 (+35.4%)** |
| 35B-A3B MoE `-sm layer` | pp4096 915.02 → 952.76 (+4.1%) | 55.30 → 68.25 (+23.4%) |

That last table is 49's default and 50 together, which is why the tensor rows jump from the
+29.8% / +5.7% in the README's older scripted table. The stock `35B tensor tg128` mean carries an
sd of 3.11 across its five rounds — the highest of any arm here — so its +35.4% is the softest
number in the set; the patched arm beside it is ±0.05.

## Limits of these runs

Three rounds then five, one MoE, one dense model, one quantization each, and only the `-ub` values
quoted. CUDA graph capture on a meta device that also carries patch 49's cross-stream event handshake
worked in every run above — that configuration is precisely the 35B tensor arm — but that is one
model family at two prompt sizes, not a stress test. A three- or four-card tensor split, where the
same capture has to cover more peers, is untested: it needs the hardware. And `-sm row` was never
tried at all.
