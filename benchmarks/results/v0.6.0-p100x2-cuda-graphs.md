# v0.6.0 on 2x P100 — CUDA graphs on sm_60 (llama.cpp#27721, tested and not adopted)

Prompted by [ggml-org/llama.cpp#27721](https://github.com/ggml-org/llama.cpp/pull/27721) (open, not
merged): one line in `ggml_cuda_graph_set_enabled` that moves the architecture gate from
`GGML_CUDA_CC_VOLTA` to `GGML_CUDA_CC_DP4A`. That is 610, so it unlocks graphs for sm_61 (GTX 1080)
and **leaves sm_60 — GP100, this box — still disabled**; the author says so himself and has no sm_60
to test. This file measures the variant that would matter here: the same line to
`GGML_CUDA_CC_PASCAL` (600).

Not adopted. Three of four configurations lose, one wins big, and the win needs a condition this
set cannot express as an architecture gate.

## How it was run

2026-10-12, `x99dual`, patched arm = the 44-patch `v0.6.0` tree. The change was applied as a
generated diff (`patch -p1 -F0`, zero fuzz) against the arm tree, `ggml-cuda.cu` rebuilt, then
**reverted with `patch -R` and rebuilt again** — the arm's `ggml-cuda.cu` is byte-identical to the
published blob afterwards (`cmp` clean). No patch file in this repo contains it.

One binary, two arms, interleaved by [`../run.sh`](../run.sh) with the order reversed on even rounds:
`graphs_on` is the build directory, `graphs_off` is a directory holding a wrapper named `llama-bench`
that exports `GGML_CUDA_DISABLE_GRAPHS=1` and execs the same real binary. `is_enabled()` is
`!(disable_due_to_gpu_arch || disable_cuda_graphs_due_to_env)`, so with the gate flipped that env var
is a clean switch inside one build. Consequence: the csv `env` column reads `none` on every row —
the switch lives in the arm name, not in the runner's environment.

3 rounds per arm per config, `-t 28 -ub 2048 -fa on -p 512 -n 128`, cards cooled to 45 C between
configs. Note `-p 512`: these prefill rows are **not** comparable to the pp2048/pp4096 rows in the
other `v0.6.0-p100x2-*` files.

Proof the graphs actually engaged (rather than the gate silently doing nothing) — `llama-bench -v` on
the 27B, counting ggml's own lines: with the flip, 6× `CUDA graph warmup complete` and 64× `CUDA
Graph id N reused`; with `GGML_CUDA_DISABLE_GRAPHS=1`, neither appears.

Identical to the last printed digit, which is the expected result — a graph replays the same
launches, it does not reassociate anything. The 27B figure also reproduces yesterday's `-sm layer`
control exactly (5.2538), across a box reboot.

## Why it is not adopted, and what would make it worth taking

Graphs remove a fixed per-launch cost, so they should pay where launches are many and small. That is
what happened, and only there: the MoE under `-sm tensor` is the configuration with the most
per-token work spread across the two cards — a meta device, expert routing, and the AllReduce
hand-off per subgraph. On a dense model and on a layer split, where each device runs whole layers,
per-token GPU work already dominates and the capture/replay overhead shows up as the 0.8-3% loss
above. The PR author's own observation runs the same way in reverse: his gain shrinks as the context
grows, because the fixed cost he removes stops mattering.

So the decision is not "graphs are bad on Pascal" — it is that **an architecture gate is the wrong
place for this**. The one line would make 27B decode and 35B-layer prefill slower on every P100 to
buy 12% for the tensor-split MoE case, and `ggml_cuda_graph_set_enabled` has no visibility into which
split mode created the context. Two things follow from that:

- Anyone with a multi-P100 MoE tensor split can have the +12% today, but only by recompiling with the
  gate lowered — `GGML_CUDA_DISABLE_GRAPHS` can turn graphs off, nothing turns them on below Volta.
- If this comes back, the shape to argue for is an **opt-in environment variable** (a graphs-below-
  Volta switch, default off, same discipline as `GGML_CUDA_AR_NGPU`), not a constant change — and
  then it needs the same treatment as every other candidate: interleaved arms at the batch sizes the
  README reports, and a perplexity or logit comparison beside it.

Also unresolved on purpose: patch 49's chunked AllReduce kernel busy-waits inside a captured graph
here, and it worked (the 35B tensor arm above is exactly that combination, and its PPL is unchanged),
but three rounds on one MoE is not a stress test of graph capture against cross-stream events.
