The half takes 30 GDN layers per step: with MEGA_DEBUG on, one 12-request graphs run logs 1260 matches
and the same run with graphs off logs 69300, because a captured graph replays one launch for many steps.

Accuracy of the half against the same build with it off, per-token logits, llama-perplexity -c 256
--chunks 1 -b 1 -ub 1 --kl-divergence:
  mean KLD 0.028402 +- 0.008595, median 0.011082, 95% 0.067399, 99% 0.354102, 99.9% 0.915616, max 0.992130
so it moves the distribution in the same way the rest of MEGA does, and greedy text differs from the
per-kernel path (f06056e070b7 against c31d841d59d2 for the same prompt). Nothing here is bit-identical
to llama.cpp without the block; the exactness mode is GGML_CUDA_P60_EXACT / MEGAX.

Determinism with the half on, same build, 4 slots x 12 requests, 192 tokens, greedy:
  - one output per prompt per arm, in all four arms (MTP on/off x graphs on/off);
  - the graphs arm equals the no-graphs arm;
  - all 48 arm/request output hashes equal those of the scratch tree that the patches were authored on.
benchmarks/gdn-gather-contracts.py passes against both trees (valid conv/state chains and every refusal:
a shifted view, a wrong row stride, two gather ids, an f16 cache, i64 ids, a mismatched cache width).

Reading: the multi-token persistent kernels are what MTP wants; the GDN half is a single-token win and
costs about 2% in a four-slot MTP server, where most steps are multi-token and a cooperative grid takes
the whole device for its launch.
